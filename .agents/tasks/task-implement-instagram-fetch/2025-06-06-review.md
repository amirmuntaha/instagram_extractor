# CORS-proxy Instagram data fetch with multi-strategy fallback

The stub `fetchInstagramData()` is replaced with a real implementation that attempts to scrape Instagram post data (username, caption, image URL) via three CORS proxy services in sequence, falling back to Instagram's embed endpoint if the main page doesn't yield enough data. The results populate the form fields and render on the poster. A color-coded feedback banner tells the user what was auto-filled and what still needs manual input. Two Playwright tests cover the happy path (mocked proxy success) and the degradation path (all proxies fail).

**Watch for:** Third-party CORS proxies are untrusted intermediaries — responses can contain arbitrary HTML whose extracted URLs flow directly into `img.src` without validation (confirmed). `AbortSignal.timeout` is not supported in Safari < 16.4 and will cause silent fetch failures on those browsers (likely). The sequential proxy waterfall can block the UI for up to 60 seconds in the worst case (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The parsing layer uses DOMParser on proxy-returned HTML and feeds the extracted `og:image` URL directly into an `<img>` element's `src`. Because CORS proxies are public services under third-party control, the HTML they return is effectively untrusted input. The DOMParser approach avoids script execution, but the extracted URLs flow into the DOM without any validation that they are actual image resources or even HTTPS.

The feedback banner (`showFetchFeedback`) uses `innerHTML` with string interpolation. The interpolated values are currently hardcoded strings so injection isn't reachable, but the pattern is one refactor away from an XSS sink.

Browser compatibility for `AbortSignal.timeout(10000)` is limited — Safari added support only in 16.4, and the project has no polyfill or transpilation step. On unsupported browsers, the TypeError is caught per-proxy but all three fail identically, leaving the user waiting for timeouts on a working network before seeing the failure feedback.

Test coverage validates the mocked happy path and the full-failure path. The embed-endpoint fallback — the most likely real-world data source since Instagram strips meta tags from unauthenticated main-page responses — is never exercised in tests.

## Proxy trust boundary and URL handling

The CORS proxy list is hardcoded as three public services: codetabs, corsproxy.io, and allorigins. These services act as full HTTP intermediaries that can fabricate response bodies. The code parses whatever HTML they return via DOMParser, extracts `content` attributes from meta tags, and places those strings into form fields and into `img.src`:

```javascript
// script.js, updatePosterFromData()
const img = document.createElement('img');
img.src = imageUrl;  // <-- directly from parsed proxy HTML
```

A URL pointing to an attacker-controlled server fires a request with the user's IP/cookies, and a `data:` URI of arbitrary size could exhaust memory. Mitigation: validate `imageUrl` against a URL pattern before assignment — require `https://` scheme and restrict to known Instagram CDN hostname patterns.

## AbortSignal.timeout compatibility gap

```javascript
const response = await fetch(proxyUrl, { signal: AbortSignal.timeout(10000) });
```

On unsupported browsers this throws `TypeError` on every proxy attempt. While each error is caught, the function still iterates all three proxies (accumulating console warnings) before returning `null`. The user experiences a working network as broken. Portable alternative:

```javascript
const controller = new AbortController();
const timeoutId = setTimeout(() => controller.abort(), 10000);
try {
    const response = await fetch(proxyUrl, { signal: controller.signal });
    // ...
} finally {
    clearTimeout(timeoutId);
}
```

## Embed fallback path coverage

The conditional for trying the embed endpoint is `if (!result.username || !result.imageUrl)`. Instagram's main page typically returns a login redirect to unauthenticated clients, making Strategy 2 the actual data source in production. The existing mocked test intercepts all proxy URLs and returns successful HTML with full data, so the embed branch is never reached.

A test that returns HTML without `og:image`/`og:description` from main-page routes, then returns embed-format HTML from embed routes, would exercise this path and catch regressions in the embed parser's CSS selectors (`.UsernameText`, `.EmbeddedMediaImage`, etc.) which Instagram changes frequently.

## Locale-dependent username regex

The regex `/@([\w.]+)\s+on\s+Instagram/i` for username extraction from `og:description` hardcodes the English phrase "on Instagram". Localized Instagram pages use different phrasing ("auf Instagram", "en Instagram", "sur Instagram"). When a proxy returns a localized page, username extraction silently fails and falls through to the embed path — functional but inconsistent.

## Sequential waterfall latency

```
Proxy 1 (10s) → Proxy 2 (10s) → Proxy 3 (10s) → Embed via Proxy 1 (10s) → Proxy 2 (10s) → Proxy 3 (10s)
```

Worst-case: 60 seconds of spinner. A `Promise.any` approach racing all three proxies with a 5-second individual timeout reduces this to 5 seconds per strategy:

```javascript
async function fetchViaCorsProxy(targetUrl) {
    const promises = CORS_PROXIES.map(proxyFn => {
        const controller = new AbortController();
        const timeoutId = setTimeout(() => controller.abort(), 5000);
        return fetch(proxyFn(targetUrl), { signal: controller.signal })
            .then(r => { clearTimeout(timeoutId); if (!r.ok) throw new Error(); return r.text(); })
            .then(text => { if (!text || text.length <= 100) throw new Error(); return text; });
    });
    try { return await Promise.any(promises); } catch { return null; }
}
```
